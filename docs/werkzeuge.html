Werkzeuge

Vier Herkünfte, ein Verzeichnis — die Executive sieht keinen Unterschied, woher ein Werkzeug kommt.

Eingebaut

search_memory, remember, list_tasks, add_task, run_command, http_get — ab Werk dabei.

Skills

Zwei Arten, beide im Skills-Ordner (HUNCH_SKILLS_DIR, Vorgabe ./skills):

  • SKILL.md — eine Anleitung für das Modell (OpenClaw-Art)
  • Python-Dateien mit run(arguments) — werden ausgeführt (Hermes-Art)

MCP

Werkzeuge fremder Server aus mcp_config.json, dynamisch geladen. Eine Config-Zeile genügt.

REST

Schnittstellen aus connectors.json — ohne eine Zeile Code.

Externe Agenten (Harnesses)

Codex, Claude Code, Gemini CLI, Aider — die Runtime kann sie starten und ihr Ergebnis zurückgeben. Eingebaut sind vier; GET /runtimes sagt, welche davon auf dieser Maschine tatsächlich liegen. Ein eigener kommt als Konfiguration dazu, ~/.hunch/harnesses.json:

{"harnesses": {"meiner": {"command": ["mein-agent", "--headless"],
                          "name": "Mein Agent", "timeout": 600}}}

Für das Modell ist das ein einziges Werkzeug, run_agent, mit dem Agenten als Argument — die Wahl „welcher" soll die Werkzeugliste nicht aufblähen.

run_agent ist immer kritisch eingestuft, unabhängig vom Auftrag. Ein fremder Agent bringt seine eigene Loop mit: er liest, ruft Werkzeuge auf, schreibt — und nichts davon geht durch den Governor oder ins Protokoll dieser Runtime. Die Freigabe vor dem Start ist die einzige Kontrolle, die dann noch greift. Dazu Zeitgrenze, gekappte Ausgabe und eine Positivliste für Umgebungsvariablen, damit der Kindprozess nicht sämtliche Schlüssel erbt.
